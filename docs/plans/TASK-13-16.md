# Plan: TASK-13…16 — Merchant-facing surface: fees, scoping, export, dashboards

Approved as a batch ("build all of that"). Sequence matters: 13 (fees) and 14 (scoping) are independent backend foundations; 15 (export) builds on 14's scoping; 16 (dashboards) consumes 13 + 14.

## TASK-13 — Fee aggregation

- Repository: `@Query` aggregate — sum of FEE transactions joined through payments, grouped by merchant, plus overall total. Fees are gateway revenue in the payment's currency; report as string amounts (exact decimal), per currency, since USD conversion is indicative only. Response: `{ merchants: [{merchantId, businessName, currency, totalFees, feeCount}], total: {currency, totalFees, feeCount} }`.
- Endpoint: `GET /api/fees` — internal surface (ops/finance); registered alongside merchants outside the payment filter.
- Tests: seed payments with fees across two merchants + currencies; assert per-merchant rows and overall totals; empty DB → zeros.

## TASK-14 — Scoped merchant auth

- Today any ACTIVE key reads every merchant's payments. Add two key tiers: a key is either a **merchant key** (bound to one merchant) or the **internal key** (`INTERNAL_API_KEY` env; when set, it bypasses merchant binding for ops/portal/export use).
- Filter change: resolve merchant as today, but also set an `internalRequest` attribute when the presented key equals the internal key. `PaymentController.list` enforces: merchant key → forced `merchantId=<self>` (a differing explicit merchantId → 403); internal key → arbitrary/omitted merchantId.
- `GET /api/payments/{id}`: merchant key on someone else's payment → 404 (not 403 — don't leak existence).
- `GET /api/fees`: internal key only → 401/403 for merchant keys.
- Back-compat: when `INTERNAL_API_KEY` is unset, behavior must be configurable-but-safe: default **deny-cross-merchant** (portal gets a real key per env docs). Update portal README/env docs.
- Tests: merchant A cannot list/read merchant B's payments (forced scoping + 404), internal key sees all, fees endpoint rejects merchant keys.

## TASK-15 — CSV export

- `GET /api/payments/export?merchantId=&status=` → `text/csv` (Content-Disposition attachment), streaming rows: id, merchantId, amount, currency, status, description, idempotencyKey, createdAt. Scoped exactly like list (TASK-14). Reads via the paged repository in chunks (500/page) to stay bounded.
- Test: export reflects scoping + filters, header row, escaping of quoted fields.

## TASK-16 — Dashboards

- **Merchant dashboard**: server-rendered **inside the backend** (Thymeleaf, single `dashboard.html` + minimal CSS, `/dashboard` route, authenticated by the merchant's own `X-API-Key` supplied via query param `?key=` on first load then a short-lived cookie to keep URLs clean). Shows: own payments (paged), captured/refunded totals, fee entries, CSV export link. No new framework in the repo; avoids a third Node app. Chosen over a separate SPA because the audience is one merchant, the data is one query, and ops runs the same jar.
- **Finance fees view in admin portal**: `/fees` page in the Next.js portal (session-gated already) consuming `GET /api/fees` — per-merchant table + overall row, ledger design tokens.
- Tests/walkthrough: backend dashboard renders scoped data for a merchant key; fees view renders totals; both walkthrough-verified.

## DoD (per task)

- Tests fail-on-unmodified-code; full suite green; portal build green where touched; walkthrough evidence; review scan; commit + record-progress each.
